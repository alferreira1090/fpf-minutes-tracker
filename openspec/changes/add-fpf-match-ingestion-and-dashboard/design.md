# Design

## Context

Greenfield. The functional baseline is the FPF skill: an extractor script (`lxml`, XPath on the saved FPF page) plus calculation rules and an Excel layout. The report pages observed in the project (`j1_fama_sub16.html`) expose: title in `og:title` ("Home vs Away — dd/mm/yyyy | Resultados FPF"), `og:url` with `matchId`, competition in `.current-competition`, final score in `.game-resume strong`, `timeline-title` + `timeline-wrapper` blocks per half (with `end-game` markers such as `45'` and `90' + 3'`), `timeline-item` events identified by icon file name, and `Equipas Iniciais` / `Suplentes` sections whose players carry shirt number, name, and an image URL `/Player/Logo/<id>`.
The user works in Portuguese and prefers a dark editorial look (navy/cream, teal accent, Fraunces / DM Sans / JetBrains Mono).

## Goals / Non-Goals

**Goals:**
- One pure, I/O-free domain core (parse → compute → aggregate) that is fully unit-tested and mirrors the skill rules.
- Store facts (one participation row per player-match), derive totals at read time, so replacing a match can never leave stale totals. This is the web equivalent of the Excel `SUMIF` formulas.
- A small deployable footprint: one process, one SQLite file.

**Non-Goals:**
- Authentication, roles, multi-tenant isolation (next change; v0.1 is localhost only).
- Scraping the FPF site; Excel export; manual identity merge UI.

## Decisions

- **Python 3.12 + FastAPI + Jinja2 + SQLite (stdlib `sqlite3`).** Reuses the skill's `lxml` extraction directly, one language end to end, `/docs` OpenAPI for free. *Alternatives:* Node/Next.js (rewrite of the extractor, heavier toolchain); Postgres from day one (operational cost with no v0.1 benefit; the repository layer keeps a later move cheap).
- **Server-rendered pages with a little vanilla JS** (column sorting, file drop). *Alternative:* SPA — more moving parts, no benefit for read-mostly tables.
- **Layering:** `domain/` (parser, minutes, identity, metrics — pure functions on dataclasses) → `storage/` (schema, repository) → `services/` (ingest orchestration) → `web/` (routes, templates). Tests target `domain/` heavily.
- **Match identity:** FPF `matchId` from `og:url`; fallback composite key (competition, date, home, away). Re-upload deletes and re-inserts the match's participation rows in one transaction, preserving the match's duration correction.
- **Player identity:** FPF player id from the roster image URL first, normalised name second. Assumption to verify on real data: the id in `/Player/Logo/<id>` is stable across matches and competitions. Different ids with the same name are never merged; same name with an id-less record merges and is logged as "merged by name".
- **Substitution/card/goal attribution by simulated state, not by name alone:** both squads are simulated; an event belongs to the team whose current state accepts it (incoming player on the bench and unused, outgoing player on the pitch). Needed because opposing squads can contain the same name (seen in the sample report).
- **Time model:** every timeline stamp becomes elapsed minutes: first half `base + added`; second half `base + added + S1`. Half-time-mark substitutions with S1 > 0 are treated as half-time and warned. Duration overrides re-run the same calculation and are validated against all events.
- **Warnings are data:** every ambiguity yields a typed warning stored with the match; nothing is silently fixed.
- **Fixtures are synthetic.** Test pages are generated by a builder that mimics the FPF markup with invented names; real pages with minors' names stay out of the repository (`data/` is git-ignored).

## Risks / Trade-offs

- [FPF changes its HTML] → parser isolates all selectors in one module; failing parse rejects the file with a reason rather than storing partial data; fixtures document the expected structure.
- [Player id assumption wrong] → identity audit page lists every merge-by-name and every homonym so the user can verify against real data.
- [Personal data on minors in a web service] → localhost bind by default, HTML escaping, no external scripts except fonts; authentication is the first follow-up change and a precondition for any hosted deployment. (Fonts loaded from Google Fonts reveal visitors' IPs to Google; switch to self-hosted fonts before hosting.)
- [Integer-minute approximation] → documented in the UI; same convention as the skill.
- [SQLite single writer] → acceptable at this scale; one transaction per match.
